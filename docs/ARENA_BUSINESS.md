# Арена для бизнеса

Дата среза: 15 октября 2026 года. Ветка: `feature/arena-improvements`, исходная база — `origin/main`.

Это описание реализованного корпоративного среза, его зависимостей и проверок. Оно не заменяет полный аудит безопасности, нагрузочное тестирование или проверку всех экранов в браузере. Результаты итоговой браузерной проверки следует фиксировать отдельно с фактическими маршрутами и условиями.

## Аудит исходной системы

В main уже существовал корпоративный продукт внутри `/company`: общие аккаунты и JWT, компании и членства, отделы, группы, сценарии, KPI, задания и попытки, программы, сертификаты, сообщения, опросы, комментарии, календарь, 1×1, турниры, цели, достижения, интеграции и аудит. Новые таблицы пользователей, отдельная авторизация и второй движок не создавались.

Фактические проблемы исходного кода:

- `context(company_id=...)` мог незаметно вернуть другую доступную компанию.
- Scopes руководителей учитывали только точное совпадение отдела; дерево и явные связи руководителей не использовались.
- Приглашение сотрудника принимало отдел из другой компании; не было одноразовых ссылок с отзывом и сроком.
- Обновление отделов допускало циклы через несколько уровней. Руководителя сотрудника нельзя было назначить через API, наставник не проверялся по tenant.
- Администратор мог назначить владельца; не было защиты последнего активного владельца и согласия при активации приглашённого сотрудника.
- CSV preview и импорт проверяли строки по-разному.
- Часть manager endpoints проверяла роль, но не область доступа: комментарии, группы, опросы, турниры, отраслевые сравнения.
- Корпоративный KPI балл копировал Arena score без самостоятельного измерения; manager отчёты могли обновляться только после открытия сотрудником своего кабинета.
- Весь интерфейс компании был сосредоточен в одном `Company.jsx`; отдельных адресов, корпоративного входа и рабочего пространства не было.

Baseline до изменений: 15 профильных backend тестов прошли; production build frontend прошёл. Материалы в тестах направлялись во временный каталог. Проверки не использовали реальные ключи LLM. В сборке оставалось предупреждение Vite о крупном чанке Three.js.

## Карта зависимостей и high-risk изменений

| Область | Зачем менялась | Потребители и сохранённый контракт |
| --- | --- | --- |
| `frontend/src/App.jsx` | Добавить `/business/*`, вложенные play/report/room и guard корпоративного входа | Все прежние личные адреса остаются зарегистрированы. `BusinessSessionBoundary` дополнительно проверяет соответствие сессии выбранной компании |
| `frontend/src/pages/Login.jsx` | Переиспользовать форму для корпоративного бренда, текста и возврата | Необязательные props с прежними значениями по умолчанию; тот же backend login/register. `auth.jsx` и `api.js` не заменялись |
| `backend/app/auth.py` | Временный demo JWT должен быть технически ограничен своей компанией | `create_token` получил необязательный keyword `business_demo_company_id`; обычные вызовы и срок обычных токенов прежние. Demo guard применяется только к public sandbox токенам и аккаунтам |
| `backend/app/main.py` | Подключить company invitations, business leads и demo API | Новые роутеры зарегистрированы до SPA fallback. Существующие роутеры и запуск приложения сохранены |
| `company.py`, `company_access.py`, корпоративные роутеры | Защитить company_id, role и scope, переиспользовать корпоративные данные | Прежние endpoints сохранены; новые поля context/permissions аддитивны. Некорректный tenant теперь получает 403. Раньше разрешавшиеся обходы прав намеренно отклоняются |
| `services.py`, `routers/game.py`, `company_workflows.py` | Согласовать corporate snapshot, hints/exam, выдачу результата и синхронизацию попыток | Backend остаётся источником канонического состояния. Метрики только trust/goal/control/eq в 0–100. Личные сессии не присваиваются чужому корпоративному заданию |
| `company_models.py`, `business_models.py`, Alembic | Добавить недостающие invitation/lead записи и поля существующих membership/cohort | Новых таблиц аккаунтов и движка нет. 0032 → 0033 продолжают текущую цепочку миграций; прежние строки сохраняются |
| `frontend/src/company/` | Постепенно убрать монолит Company.jsx и дать разделам отдельные адреса | Общие модули для legacy и B2B, существующий API client; нет второй реализации корпоративных действий |

При обычном corporate входе JWT подтверждает пользователя, а `require_membership` и scopes проверяют каждую компанию и действие. Выбор компании в UI сам по себе прав не даёт. COMPANY_OWNER, COMPANY_ADMIN, LND_MANAGER, DEPARTMENT_MANAGER, TEAM_LEAD, EMPLOYEE сохраняют свои значения; должность остаётся отдельным полем.

## Миграции и проверка

- `0032_business_access`: `company_invitations`; `company_memberships.personalization_enabled` с default 0; leader/dates/goal/focus_skills в существующей `company_cohorts`.
- `0033_business_sales`: `business_leads` с версией согласия и индексами лимитов. Сетевой адрес хранится в виде HMAC, конфиденциальные контакты не выдаются публичным GET.
- Для рабочей установки применяется штатная команда из `backend`: `python -m alembic upgrade head`. Сначала нужна резервная копия и штатная процедура установки проекта.
- 0032 проверена upgrade → downgrade до 0031 → upgrade на временной копии существующей SQLite: 23 membership сохранены; исходная рабочая БД этим тестом не менялась. 0033 также проверена на чистой БД и копии существующей установки.
- После D + workflow изменений выполнен профильный прогон: 24 теста passed. После регистрации настоящего demo API выполнен отдельный прямой прогон access/demo: 15 тестов passed. Итоговый полный backend прогон: 196 passed, 1 skipped. После последнего уточнения приватности отдельный профильный срез: 21 passed. Финальная production-сборка frontend прошла.
- Набор проверок: `tests/test_company.py`, `test_company_certificate_pdf.py`, `test_company_business_access.py`, `test_company_business_workflow.py`, `test_business_demo.py`; также сохраняются существующие tests scenarios/metrics.

Для воспроизводимого профильного прогона из `backend`:

```powershell
python -m pytest tests/test_company_business_access.py tests/test_company_business_workflow.py tests/test_business_demo.py tests/test_company_certificate_pdf.py -q
```

Для теста загрузки материалов в `test_company.py` нужен доступный тестовому процессу каталог. В проверках с ограниченным sandbox использовался отдельный временный `MATERIAL_STORAGE`. Нельзя направлять QA загрузки в рабочие пользовательские материалы.

## Руководство владельцу компании

1. На публичной странице выбрать «Для компаний», затем войти существующим аккаунтом или зарегистрироваться. После входа выбрать компанию либо создать новую.
2. В мастере первого запуска заполнить карточку компании, создать подразделения и назначить руководителей. У роли доступа и должности разные назначения.
3. В «Сотрудниках» пригласить существующий логин, создать одноразовую ссылку либо проверить CSV перед импортом. Человек сам подтверждает вступление. Истёкшую или ненужную ссылку можно отозвать и создать новую.
4. Создать или выбрать опубликованный кейс. У задания настроить получателей, срок, попытки, проходной балл, помощь и видимость результата. Для программы связать этапы с шаблонами заданий и зачислить сотрудников.
5. После прохождения открыть результаты/аналитику, оставить разбор, при необходимости опубликовать отложенные результаты. При выполнении условий сертификат формируется существующим генератором PDF.
6. Для перехода в другую компанию использовать переключатель. «В личную арену» меняет контекст интерфейса, а не создаёт второй аккаунт.

Руководитель подразделения видит поддерево и допустимых подчинённых; team lead — свою команду, назначенные управляемые отделы/группы и подчинённых. Полное управление компанией и составом ролей остаётся у владельца/администратора. Перед деактивацией руководителя нужно переназначить его управляемые отделы, группы и подчинённых. Последнего активного владельца деактивировать нельзя.

## Руководство сотруднику

1. Открыть ссылку приглашения. Войти/зарегистрироваться тем же личным аккаунтом и явно подтвердить вступление. При нескольких организациях выбрать нужную компанию.
2. На «Моей главной» и в «Моих заданиях» выбрать назначенное задание. Запуск создаёт корпоративную попытку в действующем движке; активная попытка возобновляется.
3. Пройти кейс. Посмотреть свой отчёт, комментарий руководителя и сертификат, если выполнены условия. Если компания отложила выдачу результатов, дождаться срока или публикации руководителем.
4. При желании включить личные рекомендации на странице практики. Они используют собственные корпоративные результаты, объясняют конкретные действия и отключаются пользователем; психологическим диагнозом не являются.
5. Личные тренировки и переписки по умолчанию не становятся корпоративными отчётами. В личную арену можно вернуться из корпоративного интерфейса.

## Демонстрационный путь

1. Открыть `/business/demo` и создать учебный кабинет. Данные изолированы от реальных компаний. Доступ действует 45 минут.
2. В кабинете пять ролей: владелец, HR/L&D, руководитель продаж, сотрудник продаж и сотрудник поддержки. Есть два отдела, две группы, два опубликованных кейса, задания, одна программа и памятка.
3. Начать владельцем: показать структуру, сотрудников и задания. Исходная аналитика содержит **0 завершённых попыток**, сертификатов ещё нет.
4. В панели демо выбрать сотрудника продаж, открыть назначенные «Переговоры с клиентом» и пройти офлайн-кейс.
5. Переключиться на руководителя продаж. Открыть фактически полученный результат и обновившуюся аналитику; посмотреть сертификат после выполнения условий. HR и владелец имеют более широкую область, сотрудник поддержки не видит чужую сессию.
6. Нажать «Завершить демо». Frontend восстанавливает прежний токен пользователя, сохранённый на время демонстрации; отдельной системы аккаунтов нет.

Технические ограничения demo: 3 создания на сетевой адрес в час, глобальный предел 30 demo-компаний в час, 20 запусков сессий на demo-пользователя и лимит изменяющих действий. JWT ограничен одной demo-компанией, её разрешёнными корпоративными API и собственными офлайн-сессиями. Приглашения реальных людей, CSV, загрузки, внешние интеграции, личные/social API, AI и голос в demo запрещены. Demo-компании имеют статус DEMO и исключены из обычного поиска компаний и отраслевых сравнений.

## Что остаётся за пределами среза

- Полноценные дополнительные роли наставника/аудитора и настраиваемые назначения capabilities. Связь наставника есть; превращать обычного сотрудника в менеджера через неё нельзя.
- SSO/SAML/OIDC, настоящая HRIS/LMS синхронизация и проверка внешних мессенджеров/календарей на реквизитах клиента. Наличие формы CompanyIntegration не доказывает работающую внешнюю интеграцию.
- Межкорпоративные лиги, marketplace, модерация пакетов практиков и сложный сезонный регламент. Текущие внутренние турниры и цели сохранены.

### Дизайн и применённые навыки

Использованы установленные по запросу пользователя Impeccable, Taste Skill, UI/UX Pro Max и emil-design-eng. Сохранены Manrope, лесной фон, сова и зелёно-персиковая палитра. Business shell рассчитан на рабочие действия, публичная страница — на выбор продукта; личный интерфейс не перерисовывался.

| До проверки | После | Причина |
| --- | --- | --- |
| Мелкий основной текст лендинга, 13 px | Основной текст 16 px | Читаемость на desktop и mobile |
| Повторяющиеся одинаковые контейнеры публичных разделов | Открытая композиция, отдельный вводный лист и форма | Более ясная иерархия и меньше визуального шума |
| Повтор shell/module заголовков | Один видимый заголовок раздела, legacy сохраняет свои | Убрана лишняя вертикальная высота |
| Offscreen навигация получала Tab, фокус мог уйти под меню | Inert фон, focus trap, Escape, возврат фокуса | Полноценное управление с клавиатуры |
| Профиль исчезал в мобильной шапке | Доступная по имени иконка профиля, цель 44 px | Сохранён путь к профилю |
| Публичный бренд импортировал весь corporate layout | Независимый BusinessBrand | Разделение загрузки public и workspace |

Impeccable detector для изменённых UI файлов вернул `[]`. Taste lint публичного JSX — без замечаний. Taste browser inspector не нашёл переполнений, сломанных изображений и низкого контраста; обнаруженный текст 13 px исправлен. Его пожелания добавить несколько фотографий, видео и движение сознательно не приняты: в этом срезе используются существующий фирменный лесной фон и спокойный B2B интерфейс. Это ограниченное отступление от Taste, а не заявление о полностью зелёном его отчёте. Шумные entrance/scroll анимации не добавлялись; короткий feedback кнопок учитывает reduced motion и pointer.

Независимый финальный review проверил desktop/mobile screenshots и исходники. Найденный недостающий selector для повторных заголовков сотрудников и структуры исправлен. Полный аудит assistive technologies и всех браузеров не проводился.
