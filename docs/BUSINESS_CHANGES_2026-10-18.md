Дата подготовки: 18 октября 2026 года.

Ветка: `sukhovskiy.a.a/business-testing-oct18`.

База сравнения: `main` на коммите `7a90e0a8e7ad4efb66b8c14e501d0fbd9628db9c`
(`feat(profile): simplify profile and unify appearance shop`).
Это последняя полученная из origin версия main на момент подготовки отчёта.

исправления и переносимый набор тестовых данных.

## 1. Общий результат

Объём поставки относительно main: **61 файл, 2032 добавленные строки, 302 удалённые строки**, включая документацию и скрипт тестовых данных.

## 3. Две точки входа на главной странице

В шапку возвращены две кнопки «Войти» с подписями аудитории:

| Точка входа | Для кого | Что доступно при регистрации |
| --- | --- | --- |
| Участникам | Личные пользователи и сотрудники компаний | «Для себя» или «Участник компании» |
| Руководителям | Создатели компаний | Создание профиля и компании в одной форме |

Корпоративный вход выделен основным зелёным оформлением. Оба пути доступны
также в мобильном меню и нижней части лендинга. Ссылки внутри формы позволяют
перейти к другому варианту входа без повторного набора данных в той же форме.

Разделение проверяется сервером через необязательное поле `portal` в запросе
входа. Сначала проверяется пароль, затем тип входа:

- создатель активной компании входит через вариант для руководителей;
- обычный пользователь, сотрудник, администратор компании или менеджер обучения,
  не создававший компанию, входит через вариант для участников;
- при неверном выборе возвращается понятное сообщение 403 без выдачи токена;
- прежний программный вход без `portal` продолжает работать;
- активная компания определяется сервером, а не произвольным ID из формы;
- явный допустимый адрес возврата сохраняется; обычный корпоративный вход ведёт
  в обзор выбранной сервером компании;
- администратор сайта направляется в административный интерфейс.

Создатель компании после авторизации может перейти в личную Арену через меню.
Разделение начальных кнопок не превращает личное и рабочее пространства в два
отдельных аккаунта.

Файлы: `frontend/src/pages/LandingPage.jsx`, `landing.css`, `Login.jsx`,
`frontend/src/business/BusinessAccess.jsx`, `backend/app/routers/auth.py`,
`backend/app/schemas.py`.

## 4. Регистрация: компактная форма и создание компании рядом

Переработана компоновка модального окна:

- обычная регистрация имеет компактную ширину;
- при регистрации создателя справа появляется блок «Данные компании»;
- окно плавно расширяется; отдельная страница заполнения компании не открывается;
- на узком экране блоки размещаются последовательно;
- форма прокручивается внутри доступной высоты;
- кнопка отправки находится после прокручиваемой области;
- скрытая корпоративная панель не занимает высоту: это устраняет большой пустой
  участок между паролем и кнопкой;
- при смене режима область формы возвращается к началу;
- сохраняются закрытие по Escape, возврат фокуса, клавиатурная навигация и
  сообщения об ошибках.

Состав личной части: имя обращения, логин, почта при включённой почтовой функции
или при создании компании, пароль с переключателем видимости. Участник компании
дополнительно указывает код организации.

Убраны лишние подписи и пояснения: «Создаю профиль», «ФИО —», подсказка о полном
ФИО, маркетинговое описание под заголовком регистрации, развёрнутый текст про
«Ваше рабочее пространство», отдельный заголовок «25 человек на старте».
Остались понятные названия полей и необходимые условия.

Корпоративная часть содержит название и необязательную отрасль. Указывается,
что начальный размер команды — 25 человек и его можно менять в настройках.
Текст о результатах уточнён: руководитель видит достижения и отчёты сотрудников
по корпоративному обучению.

Файлы: `frontend/src/pages/Login.jsx`, `registration-options.css`,
`frontend/src/business/BusinessLayout.jsx`.

## 5. Серверная регистрация и создание рабочего пространства

Расширен контракт `RegisterIn`:

- `registration_kind`: `personal`, `participant`, `company`;
- `full_name`: нормализованное имя обращения;
- `company_code`: код из 10 символов;
- `company_details`: название и отрасль;
- сохранены отдельные компоненты ФИО из актуального main.

Для создателя обязательна электронная почта, даже если SMTP ещё не настроен.
Проверяются формат и занятость адреса. При включённой почтовой функции создаётся
письмо подтверждения. API `/auth/me` отдаёт имя и его компоненты для интерфейса.

Профиль и компания создаются в одной транзакции. При ошибке создания рабочего
пространства незавершённый пользователь не остаётся в базе. Новая компания получает
владельца, подписку TEAM/TRIAL на 25 мест и запись аудита.

Общий код вынесен в `company_registration.py`: и регистрация, и существующее
создание компании используют один механизм. Старый экран создания компании для
уже авторизованного пользователя сохранён, также требует почту и использует
тот же размер команды.

`TokenOut` дополнен необязательным `company_id`, чтобы интерфейс после успешного
создания открыл именно созданную компанию.

Файлы: `backend/app/company_registration.py`, `routers/auth.py`,
`routers/company.py`, `schemas.py`, `frontend/src/pages/CompanyRequestSent.jsx`.

## 6. Код компании и заявки на вступление

У компании появился уникальный код вида `ABCD-EFGHJ`: девять символов из
латинских букв и цифр плюс дефис, всего десять знаков. Генератор исключает
некоторые визуально похожие символы. В базе действует ограничение уникальности.

Новая миграция `0051_company_join_code` добавляет поле и заполняет коды для
существующих компаний. Проверено сохранение компаний, уникальность кодов,
повторное выполнение и откат миграции.

Регистрация участника по коду создаёт заявку, а не немедленное членство.
Руководство получает уведомление. До одобрения пользователь не получает доступ
к корпоративным данным. После отправки открывается отдельное подтверждение.
Повторная активная заявка или попытка вступить в уже доступную компанию
обрабатывается существующими проверками.

Большая карточка кода убрана с главной страницы бизнеса вместе с описанием,
надписью «10 символов» и отдельной кнопкой копирования на этом месте. В нижней
части боковой панели остаётся только `Код: …`. Расширенный компонент кода
используется там, где человек непосредственно добавляет сотрудников.

Сам код отдаётся в контексте компании только при разрешении `invite_members`.
Обычные сотрудники его не получают через этот ответ API.

Файлы: `backend/app/company_models.py`, `alembic/versions/0051_company_join_code.py`,
`company_registration.py`, `routers/company.py`, `frontend/src/company/CompanyJoinCode.jsx`,
`company-join-code.css`, `employees.jsx`, `platform.jsx`, `business/BusinessLayout.jsx`.

## 7. Единое меню профиля и переключение компаний

Создан `ProfileWorkspaceMenu`, используемый обоими интерфейсами. В меню доступны:

- имя текущего пользователя;
- переход в профиль текущего пространства;
- личная Арена;
- все активные компании пользователя с названием его роли;
- отметка текущего пространства;
- ссылка на приглашения, если они есть;
- выход из аккаунта.

Компании загружаются через существующий `/api/company/context`. Нет второго
клиента API, дополнительного хранилища авторизации или отдельного входа для
каждого пространства. Список фильтруется по активному членству, а переходы
проходят существующую серверную проверку прав.

Предусмотрены загрузка, отсутствие компаний, ошибка и повторный запрос. Меню
открывается наведением, фокусом и нажатием; закрывается при уходе фокуса, клике
снаружи, переходе и Escape. Escape возвращает фокус к аватару.

В демонстрационном бизнес-режиме переключение отключено, а выход использует
существующий механизм восстановления исходной сессии. На личной странице профиля
добавлены ссылки во все рабочие пространства вместо подписи только первой компании.

## 9. Календарь и создание мероприятий

Подпись месяца теперь имеет вид «Октябрь 2026», без «г.». Удалено длинное
пояснение про обучение, практики, сценарии и соревнования в одном расписании.
Заголовок страницы не дублируется внутри самого календаря.

Для пользователей с `manage_team` на месте «Сегодня» находится кнопка
«Добавить мероприятие». Остальным оставлена навигационная кнопка «Сегодня».
Открывается диалог с двумя форматами:

**Встреча 1×1:** выбор двух разных активных сотрудников, времени, названия,
ситуации, цели и длительности от 2 до 30 минут. Используется существующий
компонент календаря выбора времени и корпоративный API бронирования.

**Совет решений:** доступен владельцу. Четыре участника, закрытая игра,
создатель выступает организатором; можно выбрать до четырёх приглашённых.
Сохраняются действующие ограничения времени: минимум через 12 часов,
в пределах двух недель. После создания есть переход к созданной игре.

После сохранения календарь обновляет события. Ссылка на Совет ведёт в саму
игру, а не обратно на страницу календаря. Предусмотрены ошибки API и состояние
отправки, чтобы повторное нажатие не создавало дубликат.

На сервере исправлено присоединение приглашённого участника 1×1: при нескольких
сгенерированных ролях явно передаётся первая доступная роль. Это устраняет ошибку
бронирования уже выбранной пары. В датах бронирований и событий добавлено
обозначение UTC, чтобы браузер корректно показывал местное время.

Файлы: `company/CalendarEventForm.jsx`, `engagement.jsx`,
`business/business.css`, `backend/app/routers/company_online.py`,
`routers/company_organization.py`.

## 10. Профиль организатора и корпоративная аналитика

Для владельца компании профиль отражает роль организатора:

- в обзоре используется управленческая сводка;
- аналитика показывает результаты компании;
- скрыты личные вкладки заданий, сертификатов, карьеры и повторный вход в
  развитие команды.

Пользователи с `view_analytics` получают корпоративный экран результатов.
Сотрудники без этого права продолжают видеть свои результаты.

В AI-профиле отображаются имя авторизованного пользователя и понятная роль,
например «Администратор компании», вместо технического `COMPANY_ADMIN` в карточке
«Права». Изменение подписи не повышает полномочия и не подменяет сотрудника
владельцем. Обновление данных учитывает смену компании и членства.

Для владельца скрыто неуместное предупреждение о передаче его записей компании.
Для сотрудников сохранено объяснение доступа к личному архиву.
Неясные «Источники: не выбраны» и «Включить» заменены объяснением использования
результатов корпоративных заданий, действием «Учитывать результаты» и переходом
к обучению. Это делает следующий шаг понятным при первом посещении.

Файлы: `company/platform.jsx`, `advanced.jsx`, `employee-cabinet.jsx`,
`results.jsx`, `business/BusinessLayout.jsx`.

## 11. Отчёты в завершённых заданиях

членства и правила публикации результатов. Доступ к чужим отчётам не выдаётся
через добавление кнопки.

Файлы: `company/AssignmentReports.jsx`, `attempt-report.jsx`, `learning.jsx`,

## 12. Карта компании: уровни, стрелки и перемещение

Вместо ряда карточек построена иерархия сверху вниз. Владелец располагается на
верхнем уровне; руководители и сотрудники — ниже. Реальные отношения подчинения
проводятся сплошными стрелками. Если руководитель сотруднику не назначен,
принадлежность к компании показана пунктирной связью с владельцем и объяснена
легендой. Эти связи не записывают выдуманного начальника в базу.

Руководящие роли выделены красной рамкой. Можно:

- перетаскивать отдельные карточки;
- перемещать карту и менять масштаб;
- двигать сфокусированную карточку клавишами-стрелками;
- сворачивать и разворачивать ветви;
- искать людей и фильтровать подразделение;
- переключаться между иерархией и специальностями;
- вернуть стандартное расположение.

При перемещении стрелки следуют за карточками. Координаты сохраняются локально
для каждой компании в `arena-company-map-{companyId}`. Это настройка браузера,

## 14. Локальная почта для разработки

Добавлен выключенный по умолчанию `DEVELOPMENT_MAILBOX`. При явном включении
письма сохраняются локально без SMTP. Это позволяет проверить подтверждение
адреса, вход по подтверждённой почте и восстановление пароля.

В административных настройках появился локальный ящик: обновление списка,
просмотр получателя, темы, текста и ссылки из письма. Показываются последние
100 локальных писем. Чтение не погашает ссылку.

API `/api/admin/mail/inbox` требует администратора, включённого режима и
loopback-соединения. Для других случаев возвращается 404. Локальные письма
имеют отдельное состояние `local` и не начинают отправляться при последующем
переключении на SMTP. Настройка SMTP при активном режиме разработки блокируется
с объяснением; для обычной почты флаг нужно выключить и перезапустить сервер.

Файлы: `backend/app/config.py`, `mail_service.py`, `routers/mail.py`,
`backend/.env.example`, `frontend/src/components/LocalMailbox.jsx`,
`local-mailbox.css`, `MailAdmin.jsx`, `README.md`.

Скрипт создаёт владельца `dododo`, администратора `dododo_admin`, менеджера

Через штатные API выполняются регистрация, отправка и одобрение заявок,
назначение обучения, прохождение сценария и получение отчётов. В чистой базе:
шесть активных членов, три задания × пять участников, шесть завершённых попыток,
девять оставшихся назначений. У Елены два отчёта, у остальных участников по одному.

сбоя возможен повторный запуск. ID и код компании получает от сервера.

Контрольный запуск на пустой базе: средний балл 56, доверие 53, цель 56,
контроль 67, EQ 48. Сводка строится из шести реальных попыток пяти участников.

пользователи не копируются в ветку. Данные воспроизводятся командой на установке

## 17. Что нужно при обновлении и практические ограничения

1. Получить новую ветку и установить обычные зависимости проекта.
2. Выполнить `alembic upgrade head`: требуется миграция `0051_company_join_code`.
3. Перезапустить API и собрать/запустить frontend из той же ветки.
4. Для командной проверки выполнить скрипт тестовых данных.
5. Для проверки локальной почты отдельно включить режим разработки; для
   регистрации и отчётов тестовой компании он не обязателен.

Отдельный релиз, деплой на общий сайт и слияние новой ветки в main этой поставкой
не выполняются. Наличие ветки в Git само по себе не переносит содержимое локальной
базы в уже работающий сервер.

Скрипт готовит аккаунты и корпоративные отчёты; локальные вручную созданные
встречи в набор не включены. Их можно назначить из календаря. Голос, внешние
LLM, SMTP-провайдеры и видеосвязь не проверялись как внешние сервисы этой отправки.
В контрольном окружении голосовые модели отсутствовали, что не мешало offline
сценариям и созданию отчётов.

Границы доступа сохраняются: корпоративный руководитель видит корпоративные
результаты в пределах своей роли; личные тренировки и архивы не становятся
общедоступными в результате изменения подписей интерфейса.
