# Защита проекта

## Назначение
Защита студенческого, внутреннего или клиентского проекта.

## Типовые роли
- автор/команда
- комиссия/заказчик/руководитель

## Интересы сторон
- автор: доказать ценность/качество
- оценщик: проверить решение, риск и понимание

## Возможные скрытые цели
- проверить самостоятельность
- выявить слабое допущение
- оценить реакцию на критику

## Базовая последовательность
- проблема
- решение
- доказательства
- критический вопрос
- ограничения
- альтернативы
- вывод

## Критичные метрики
- Goal
- Control
- Trust

## Грубые ошибки
- выдуманные данные
- атака на критика
- уход от ограничения

## Сильные ходы
- признание ограничения
- данные
- сравнение альтернатив
- структурированный ответ

## Варианты
- студенческий
- внутренний бизнес
- технический
- инвестиционный

## Правила генерации
- 6–8 шагов.
- На каждом шаге 3–4 ответа игрока.
- Дельты Trust/Goal/Control/EQ в диапазоне -6..+6.
- Каждый ответ должен менять либо состояние, либо информацию, либо отношения.
- Минимум три различимых финала.
- Сценарий должен быть проходимым.
- BATNA/ZOPA задавать только при наличии достаточных фактов.
- Реплики должны быть разговорными, без академической сухости.
- Оценка профессиональной части берётся из соответствующего файла `professions/`.
- Переговорная оценка берётся из `negotiations/`.

## Ограничения
Не подменять профессиональную оценку личными симпатиями. Актуальные юридические требования проверять отдельно, если они существенны для сценария.
